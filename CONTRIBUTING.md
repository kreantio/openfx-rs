## Decisions

### Code and data generation

[The `openfx` crate] relies heavily on code generation. Both the bindings in the
`sys` layer and most of the code in the `low` layer are generated from data
stored in [`openfx-data`] by [`openfx-codegen`] (which is currently an
unpublished crate).

The data are generated by [`openfx-datagen`] from the official C headers in
[the openfx repository]. They fall into two categories:

- Bindings data: They contain the structural data used to generate bindings.
  [`openfx-codegen`] uses them to generate the bindings in the `sys` layer and
  some of the code in the `low` layer. [`openfx-datagen`] produces them by
  parsing the code in the official C headers.
- Metadata: They contain additional information about the OpenFX API.
  [`openfx-codegen`] uses them to generate some of the code in the `low` layer.
  [`openfx-datagen`] produces them by parsing the comments in the official C
  headers.

The whole code generation pipeline is written in Rust to reduce friction.
`treesitter` is used for parsing the C code so that `clang` is not a dependency.

The generated data are stored in a separate repository, [`openfx-data`], to
avoid bloat in the main repository. As a side effect, [`openfx-datagen`] has to
live in another repository to avoid a circular dependency.

The generated code is checked into this repository, so that users of
[the `openfx` crate] do not need to pull in the build dependencies and run
`build.rs`. This keeps [the `openfx` crate] very lightweight (currently with 0
dependencies). To avoid bloat, macros (both procedural and declarative) are used
extensively.

## Terminology

### Terms for Property Names

This project refers to properties in three ways:

- **Cname** are macro names defined in the OpenFX C headers, such as
  `kOfxPropAPIVersion`.
  - They always begin with `k`.
  - This is a term that appears in the official repository[^1].
- **Canonical names** are cnames with the leading `k` removed, such as
  `OfxPropAPIVersion`.
  - This is not an official term.
- **Stringname** are the values of key-value macros, such as
  `OfxPropAPIVersion`.
  - Most match their canonical names, but some are irregular. For example, the
    property with canonical name `OfxPropKeyString` has the key constant
    `kOfxPropKeyString` rather than `OfxPropKeyString`: the `k` was included in
    the key constant.
  - This is a term that appears in the official repository[^2].
- **Simple names** are cnames with the leading `kOfx` removed.
  - This is not an official term.

In this project, the `sys` layer exposes properties by their cnames, while other
layers, such as the `low` layer, use their canonical names (or simplified forms
derived from those names). Because the official C++ headers use key constants,
processing must map those values back to canonical names.

#### Examples

```c
// ofxCore.h:
#define kOfxPropAPIVersion "OfxPropAPIVersion"

// ofxImageEffect.h:
#define kOfxImageEffectPropSupportsMultipleClipDepths "OfxImageEffectPropMultipleClipDepths"

// ofxKeySyms.h:
#define kOfxPropKeySym "kOfxPropKeySym"
```

| Cname                                         | Canonical Name                               | Stringname                           | Regular? |
| --------------------------------------------- | -------------------------------------------- | ------------------------------------ | -------- |
| kOfxPropAPIVersion                            | OfxPropAPIVersion                            | OfxPropAPIVersion                    | yes      |
| kOfxImageEffectPropSupportsMultipleClipDepths | OfxImageEffectPropSupportsMultipleClipDepths | OfxImageEffectPropMultipleClipDepths | no       |
| kOfxPropKeySym                                | OfxPropKeySym                                | kOfxPropKeySym                       | no       |

### Terms for Property Enum Variant Names

Property enum variant names follow the same terminology as property names.

#### Examples

```c
// ofxImageEffect.h:
#define kOfxImageComponentNone "OfxImageComponentNone"

// ofxImageEffect.h:
#define kOfxImageFieldNone "OfxFieldNone"
```

| Cname                  | Canonical Name        | Stringname            | Regular? |
| ---------------------- | --------------------- | --------------------- | -------- |
| kOfxImageComponentNone | OfxImageComponentNone | OfxImageComponentNone | yes      |
| kOfxImageFieldNone     | OfxImageFieldNone     | OfxFieldNone          | no       |

### Terms for Action Names

Action names follow the same terminology as property names.

#### Examples

```c
// ofxCore.h:
#define  kOfxActionLoad "OfxActionLoad"
```

| Cname          | Canonical Name | Stringname    | Regular? |
| -------------- | -------------- | ------------- | -------- |
| kOfxActionLoad | OfxActionLoad  | OfxActionLoad | yes      |

### Terms for Types

- **Simple types** are the types exchanged directly between OpenFX hosts and
  OpenFX plugins through the OpenFX API. They are `Int`, `Double`, `String`, and
  `Pointer`.
  - They have representations in both the `sys` layer and the `low` layer.
  - This is not an official term.
- **Expressive types** are `Int`, `Double`, `String`, `Pointer`, `Bool`, and
  `Enum`.
  - `Bool` is built on top of the `Int` simple type, `Enum` is built on top of
    the `String` simple type, and the other expressive types are built directly
    on top of their respective simple types.
  - They only have representations in the `low` layer.

Values of simple types and expressive types can be converted into each other in
either direction.
